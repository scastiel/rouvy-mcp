# OAuth authorization server options for a Rouvy-credential login

Research for [OAuth authorization server options for a Rouvy-credential login](https://github.com/scastiel/rouvymcp/issues/31), part of [Map: Hosted Rouvy MCP server — milestone 2 (web auth)](https://github.com/scastiel/rouvymcp/issues/28). Gathered 2026-10-25.

## The question, restated

The hosted server is an OAuth **resource server** (the MCP endpoint) and needs an **authorization server** (AS) that:

1. speaks the MCP authorization profile: PKCE, RFC 8414 AS metadata, RFC 9728 protected-resource metadata, RFC 8707 resource indicators, and client registration by **CIMD** and/or **DCR** (which ones claude.ai needs is settled in [MCP authorization spec and what claude.ai and other clients support](https://github.com/scastiel/rouvymcp/issues/30); this note only asks which options support which);
2. lets **our own page** be the login step: it takes Rouvy email + password, runs M1's Firebase `signInWithPassword` (`docs/spec-m1.md` §4), and has no user database of its own — the Firebase uid *is* the user;
3. attaches a **per-user upstream secret** (the Firebase refresh token, possibly rotated on refresh) to the grant;
4. keeps **self-hosting** simple, costs ~nothing at hobby scale, and does not lock the project in.

Useful fact for the custody design: Firebase refresh tokens only expire when "the user is deleted", "the user is disabled", or "a major account change is detected" (password or email change) ([Firebase: manage sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)). So the upstream secret lives as long as the rider does not change their password, and each sign-in mints an independent one. Storing one per grant is a natural fit.

## A. Cloudflare `workers-oauth-provider`

Source: [cloudflare/workers-oauth-provider README](https://github.com/cloudflare/workers-oauth-provider) (npm `@cloudflare/workers-oauth-provider` 1.2.4, MIT, updated 2026-10-22).

- **Standards.** States conformance with "MCP authorization 2026-07-28, OAuth 2.1, and RFCs 6750, 7009, 7591, 7636, 8414, 8693, 8707, 9207 and 9728, plus Client ID Metadata Documents". CIMD is a flag (`clientIdMetadataDocumentEnabled: true`) and needs the `global_fetch_strictly_public` compatibility flag. DCR, pre-registered clients and CIMD are all documented ([authorization-server.md](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/authorization-server.md)). A `conformance/` directory in the repo runs against the upstream MCP conformance suite.
- **Our login page.** "Your `authorizeEndpoint` is application code, because user authentication and consent are application-specific… The provider is not an identity provider." The flow is: `parseAuthRequest(request)` → "Authenticate the user, show consent, and decide which scopes to grant" → `completeAuthorization()` and redirect ([authorization-server.md](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/authorization-server.md)). A [consent-page guide](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/consent-page.md) covers escaping client metadata and Allow/Deny. Our Rouvy email/password form sits exactly here, with `userId` = Firebase uid.
- **Per-user upstream secret.** `completeAuthorization({ props })` stores app data on the grant. Per [storage-schema.md](https://github.com/cloudflare/workers-oauth-provider/blob/main/storage-schema.md): "Tokens, codes and secrets are stored only as hashes; `props` are encrypted with a key only the token holder can unwrap" (AES-GCM; the key is wrapped with the token itself). A KV dump alone does not reveal Rouvy refresh tokens. Grant `userId` and `metadata` are *not* encrypted.
- **Rotation / refresh.** `tokenExchangeCallback` "runs during authorization code and refresh token exchanges. It is useful when the Worker also acts as an OAuth client to an upstream service." It can return `accessTokenProps`, `newProps` (for the grant and future refreshes), `accessTokenTTL` and `refreshTokenIdleTTL`, and can throw `OAuthError` to fail the token request ([advanced-configuration.md](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/advanced-configuration.md)). For us, on every MCP refresh: Firebase `securetoken` refresh → put the 1 h `idToken` (and maybe the `rouvy_session` cookie) in `accessTokenProps`, put any rotated Firebase refresh token in `newProps`, and set `accessTokenTTL` to the `idToken` lifetime. This mirrors M1's lazy refresh with no background timers. A dead Firebase token becomes `invalid_grant`, so the client re-runs OAuth, which speaks to the re-auth UX open question.
- **Caveat of that design:** the MCP handler can read `ctx.props` but cannot write them back, so the upstream secret can only change during a token exchange. Fine if access-token TTL ≤ `idToken` TTL. Otherwise the handler must refresh the Firebase `idToken` in memory without persisting a rotated refresh token.
- **Grant lifetime.** Default 30 days absolute after the code exchange. `refreshTokenIdleTTL` makes it sliding. DCR clients expire after 90 days idle (`clientRegistrationTTL`).
- **Prior art.** Cloudflare's demos wrap third-party logins exactly this way, e.g. [`remote-mcp-github-oauth`](https://github.com/cloudflare/ai/tree/main/demos/remote-mcp-github-oauth) calls `parseAuthRequest`, does the upstream GitHub exchange, then `completeAuthorization({ props: { accessToken, … } })` ([github-handler.ts](https://github.com/cloudflare/ai/blob/main/demos/remote-mcp-github-oauth/src/github-handler.ts)). Sibling demos cover Google, Slack, Auth0, AuthKit, Descope, Stytch and Logto ([cloudflare/ai demos](https://github.com/cloudflare/ai/tree/main/demos)). Ours differs only in that the "upstream" step is a password form plus a Firebase call instead of a redirect.
- **Platform tie.** `src/oauth-provider.ts` starts with `import { WorkerEntrypoint } from 'cloudflare:workers'` and reads `env.OAUTH_KV: KVNamespace` directly. There is no storage adapter, so it does not run on plain Node. Running it off Cloudflare would mean workerd plus a KV emulation (e.g. Miniflare), which is unsupported. That last point is my inference; it is not documented.
- **Cost.** Workers Free: "100,000 per day" requests, "10 milliseconds of CPU time per invocation"; Paid has a "minimum charge of $5 USD per month" ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). KV Free: 100,000 reads/day, **1,000 writes/day**, 1 GB; ops past a limit fail ([KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)). Each code exchange or refresh writes a few keys, so the free write budget allows a few hundred token refreshes a day. That covers an invite-only instance with hourly access tokens and a handful of riders, but not much more. My estimate, from the storage schema.
- **Implication beyond auth.** Choosing A means running the MCP server itself on Workers too, or at least the AS. That pulls in questions owned by [Hosting platforms and egress to Rouvy's Cloudflare](https://github.com/scastiel/rouvymcp/issues/32) and [Probe Rouvy from candidate hosts](https://github.com/scastiel/rouvymcp/issues/33): Workers egress to a Cloudflare-fronted Rouvy, Node compat for `turbo-stream@2` / `fit-file-parser`, and the 10 ms CPU budget for FIT parsing and stats.

## B. MCP TypeScript SDK AS helpers

- The repo uses `@modelcontextprotocol/sdk` 1.32.2. Its `server/auth` ships `mcpAuthRouter` and the `OAuthServerProvider` interface: `clientsStore`, `authorize(client, params, res)`, `challengeForAuthorizationCode`, `exchangeAuthorizationCode`, `exchangeRefreshToken`, `verifyAccessToken`, optional `revokeToken` (from `node_modules/@modelcontextprotocol/sdk/dist/esm/server/auth/provider.d.ts`). `authorize` gets the Express `res`, so it can render our Rouvy form. Everything else is ours: code/token minting, storage, the refresh-token store.
- **No server-side CIMD.** The v1 types include `client_id_metadata_document_supported`, but the router only does DCR via `clientsStore.registerClient`. Nothing in `server/auth` fetches a metadata document.
- **Frozen.** In SDK v2 (`@modelcontextprotocol/server` 2.4.0) these helpers moved to `@modelcontextprotocol/server-legacy`, whose npm description reads: "Frozen v1 SSE transport and OAuth Authorization Server helpers… Deprecated; use StreamableHTTP and a dedicated OAuth server in production." The v2 docs say the same: "The Authorization Server helpers (`mcpAuthRouter`, `ProxyOAuthServerProvider`, …) are frozen in `@modelcontextprotocol/server-legacy/auth`. Use a dedicated identity provider for new servers" ([docs/serving/authorization.md](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/authorization.md)).
- **What v2 keeps (useful for every option):** the resource-server half. `requireBearerAuth({ verifier, requiredScopes, resourceMetadataUrl, expectedResource })` (Express and a web-standard `fetch` variant for Workers/Hono), `mcpAuthMetadataRouter` / `oauthMetadataResponse` for RFC 9728 + a mirror of the AS's RFC 8414 doc, and `ctx.http.authInfo` in tool handlers (same doc). Whatever AS we pick, the MCP endpoint should use these.

## C. `oidc-provider` (panva)

- [panva/node-oidc-provider](https://github.com/panva/node-oidc-provider), npm 9.13.0, MIT, OpenID Certified. Implements RFC 7591/7592 DCR, PKCE, RFC 8707 resource indicators, revocation, introspection, DPoP, PAR, and "OAuth Client ID Metadata Document (CIMD) — draft-ietf-oauth-client-id-metadata-document-02" as an experimental feature ([docs/README.md](https://github.com/panva/node-oidc-provider/blob/main/docs/README.md)).
- Login and consent are app code: `provider.interactionDetails(req, res)` then `provider.interactionFinished(req, res, result)` (same doc). The upstream secret goes in our own table keyed by `accountId` (the Firebase uid) or grant id. `extraTokenClaims` can add claims to access tokens.
- Storage: pluggable `adapter`; "The default implementation provides a basic in-memory adapter suitable for development and testing purposes only." So it needs a SQLite/Postgres/Redis adapter (ours or community).
- Watch: CIMD is draft-02 and experimental, and Better Auth's docs note that "the MCP 2026-07-28 profile explicitly pins draft-00 requirements" ([Better Auth OAuth provider](https://www.better-auth.com/docs/plugins/oauth-provider)). Whether the gap matters to claude.ai is a question for [MCP authorization spec and what claude.ai and other clients support](https://github.com/scastiel/rouvymcp/issues/30). It is also an OIDC server: lots of surface (id_tokens, userinfo, sessions, cookies) that MCP does not need.

## D. Better Auth OAuth provider

- [`@better-auth/oauth-provider`](https://www.better-auth.com/docs/plugins/oauth-provider) 1.7.12 (MIT): PKCE required by default, RFC 8707 resources become the JWT `aud`, DCR "remains supported for backwards compatibility" with CIMD via `@better-auth/cimd`, and an `mcp({ loginPage, consentPage, resource })` preset.
- Login hands off to `loginPage`, and "when a new session is created, the plugin will handle continuing the authorization flow". So the rider must end up with a **Better Auth session/user row**. That is doable with a custom sign-in endpoint that runs Firebase and upserts a user keyed by uid, but it brings a second user model, which the map rules out ("No separate rouvy-mcp accounts"). Plain Node + SQL, so self-hosting is easy.

## E. Hosted IdPs with bring-your-own-login

- **WorkOS AuthKit, Standalone Connect.** "AuthKit redirects users to your application's Login URI instead of showing AuthKit's login page". Our app authenticates the user and calls `POST /authkit/oauth2/complete` with `external_auth_id` and a `user` object (`id`, `email`, optional `metadata`). AuthKit then does consent and token issuance ([AuthKit MCP](https://workos.com/docs/authkit/mcp), [completion API](https://workos.com/docs/reference/workos-connect/standalone/complete)). CIMD "is off by default", DCR is optional. Free up to "1 million monthly active users" ([pricing](https://workos.com/pricing)), but the page doesn't say whether Connect/MCP is in that tier. Nothing attaches a secret to the grant, and putting a Firebase refresh token in `user.metadata` would hand it to a third party unencrypted. So we still run our own encrypted DB keyed by `sub`.
- **Stytch Connected Apps, Trusted Auth Tokens.** "Your existing authentication system will remain in control of the user's login experience"; Stytch "will be responsible for all OAuth client management, user consent, and token issuance". It accepts "any authentication system that issues a JWT `access_token` or `id_token` with an `email` claim" ([integrate with an existing system](https://stytch.com/docs/connected-apps/guides/integrate-with-existing-system)). The Firebase `idToken` we already get is such a JWT. Free "10,000 monthly active users" ([pricing](https://stytch.com/pricing)). The trade-offs match WorkOS, and it adds a dependency on Stytch trusting tokens from *Rouvy's* Firebase project.
- For both: each self-hoster must create a vendor tenant, configure the Login URI or token profile, and hold API keys. The "one codebase, self-hostable" path becomes "one codebase plus a SaaS account".

## F. Hosted IdPs as the user store (Auth0, Clerk, Descope)

- **Auth0.** MCP guides recommend CIMD ("For production MCP deployments, we recommend using CIMD registration") and also support DCR ([registering your MCP client](https://auth0.com/ai/docs/mcp/guides/registering-your-mcp-client-application.md)). The way to check a Rouvy password would be a Custom Database connection, whose scripts are Node.js functions run during login ([custom DB](https://auth0.com/docs/authenticate/database-connections/custom-db/overview-custom-db-connections)). The Free plan (25k MAU) lists custom database connections as **not available** ([pricing](https://auth0.com/pricing)). The Rouvy password would also be typed into Auth0's page and handled by a script on Auth0's infrastructure.
- **Clerk.** DCR toggle and beta CIMD ([Clerk MCP guide](https://clerk.com/docs/expressjs/guides/ai/mcp/build-mcp-server)). Hobby is free to 50,000 MRU ([pricing](https://clerk.com/pricing)). It has no documented external-password hook, so bridging would mean mirroring each rider as a Clerk user and minting sign-in tokens from our own backend. That is my inference of a workaround, not a documented MCP pattern.
- **Descope.** Inbound Apps as the MCP AS, with CIMD, DCR and pre-registration ([registration methods](https://docs.descope.com/agentic-identity-hub/mcp-servers/registration-methods)). Free tier "7,500" MAU and "2,000 Monthly active consents", the unit billed for MCP ([pricing](https://www.descope.com/pricing)). Plugging a Rouvy credential check into its flows is possible in principle (custom flow connectors) but not verified here.
- All three make our Rouvy login a guest inside someone else's login system. That is the opposite of the map's "the rider's Rouvy account is the only identity", and it adds a processor that sees Rouvy credentials. That last point matters for [Operator risk for a public instance](https://github.com/scastiel/rouvymcp/issues/29).

## G. Libraries that are not an AS

- **`oauth4webapi`** is a "Low-Level OAuth 2 / OpenID Connect **Client** API" ([README](https://github.com/panva/oauth4webapi)). It is the right tool for the *client* side (or for testing our AS), but it issues nothing.
- **`@node-oauth/oauth2-server`** 5.3.1: "Fully RFC 6749 and RFC 6750 compliant", with PKCE, pluggable storage via a model, and an Express wrapper ([README](https://github.com/node-oauth/node-oauth2-server)). The README lists no DCR, CIMD, RFC 8414/9728 metadata or RFC 8707, so those would be hand-built. It is effectively option B with a different model API and no MCP awareness.
- **Hand-rolling on SDK v2's RS helpers.** Possible, and the spec surface is small (authorize, token, register/CIMD fetch, metadata). But it means owning PKCE, code replay, refresh rotation, redirect-URI matching and SSRF-safe CIMD fetching ourselves. Only worth it if A and C both fail on hosting grounds.

## Assessment

- **Fit for "our page + per-grant upstream secret":** A is the only option where this is the documented, first-class pattern (`props` + `tokenExchangeCallback`), with props encrypted under the bearer token. B, C and G support it with our own encrypted table. D and E/F work against it.
- **Spec compliance with least effort:** A, then C. The hosted IdPs are compliant too but bring the self-host and identity problems. B lacks CIMD and is frozen.
- **Self-host simplicity:** B, C, D and G are "Node + a DB file" and fit a Docker image. A is "Cloudflare account + `wrangler deploy`": simple, free and arguably easier than running a VPS, but tied to one vendor. E/F are the worst (a SaaS tenant per self-hoster).
- **Cost:** everything except Auth0's custom DB is free at hobby scale. A's free KV write cap (1,000/day) is the tightest limit seen.
- **Lock-in:** A ties the AS (and probably the MCP host) to Workers. The tie stays at the edge: the `credentials` provider seam from `docs/spec-m1.md` §3 maps cleanly onto `ctx.props`, so the core does not care. E/F tie identity to a vendor.

## Recommendation

1. **Rule out** hosted IdPs (E, F) and Better Auth (D): each adds a second identity or user store, a third-party processor of Rouvy credentials, or a per-self-hoster SaaS tenant. Rule out the SDK's frozen AS helpers (B) as a foundation, since they have no CIMD and are deprecated upstream.
2. **Lead candidate: `@cloudflare/workers-oauth-provider` (A)**, *conditional on* [Hosting platforms and egress to Rouvy's Cloudflare](https://github.com/scastiel/rouvymcp/issues/32) / [Probe Rouvy from candidate hosts](https://github.com/scastiel/rouvymcp/issues/33) showing that a Worker can reach Rouvy, and that the M1 core runs on Workers within budget. It is the only option built for exactly this pattern, its props encryption is a real custody win for [Rouvy token custody on the hosted server](https://github.com/scastiel/rouvymcp/issues/35), and self-hosting becomes "fork, `wrangler deploy`, free plan".
3. **Fallback if Workers is out: `oidc-provider` (C) on Node**, with its interactions as our Rouvy sign-in page and an encrypted per-grant table holding the Firebase refresh token. First confirm that its experimental CIMD (draft-02) satisfies what claude.ai sends, or that DCR suffices, per [MCP authorization spec and what claude.ai and other clients support](https://github.com/scastiel/rouvymcp/issues/30).
4. **Either way**, the MCP endpoint uses SDK v2's resource-server helpers (`requireBearerAuth` with `expectedResource`, `oauthMetadataResponse` / `mcpAuthMetadataRouter`). Moving the hosted entry point to SDK v2 is a decision of its own, since the repo is on 1.32.2.

## Open questions surfaced

- **SDK v1 → v2.** The repo pins `@modelcontextprotocol/sdk` ^1.32.2. SDK v2 splits packages (`@modelcontextprotocol/server`, `/express`, `/node`), and the hosted RS helpers documented above are v2's. Does M2 (and stdio) move to v2 first?
- **Can the MCP server itself run on Workers?** (Node compat for `turbo-stream@2` and `fit-file-parser`, the 10 ms CPU free limit for FIT parsing and stats, egress to Rouvy.) Probably belongs in [Hosting platforms and egress to Rouvy's Cloudflare](https://github.com/scastiel/rouvymcp/issues/32), but it decides between A and C.
- **One Firebase sign-in per grant vs one per rider.** With per-grant props, each MCP client connection holds its own Firebase refresh token. A password change kills all of them at once (Firebase docs above), and our own revocation is per grant. That seems right, but [Rouvy token custody on the hosted server](https://github.com/scastiel/rouvymcp/issues/35) should confirm it.
